## Cross-cutting invariants

- Status changes through `POST /api/tasks/:id/transition` and `PATCH /api/tasks/:id` write an audit event (`task.transitioned`, or a dedicated action such as `task.backlog_promoted`). The creation audit row depends on the route. Single create (`POST /api/projects/:projectId/tasks`) and batch import (`POST /api/projects/:projectId/tasks/import`) write `task.created` with `event: task_available_signal` for each task they create in the workflow's initial state when they send `task_available` signals, so a task created in `backlog`, or in a team with no claim-eligible agent, gets no such row. Batch import also writes `task.imported` for every task it creates, backlog included. Outside the grounding creation policy, the signal row is the only creation row single create writes. On a project selected by that policy ([grounding-receipt-contract.md](grounding-receipt-contract.md#runtime-creation-policy-and-retained-history)), single create always writes `task.created` as well. A GitHub `issues.opened` webhook writes `task.created` and, when it signals, the `task_available_signal` row as well. Team repo sync writes no audit row.
- Every privileged action validates the actor's scope server-side. Token scope is the source of truth, not the client claim.
- GitHub webhook deliveries are deduplicated by delivery id: a redelivered event is skipped, so it does not double-write. Team repo sync is a synchronous request, not a background worker.

Team sync (`POST /api/teams/:id/sync`) creates or updates one project per repository visible to the syncing user, for every team member, and, only when the caller is a team `ADMIN`, deletes the team's GitHub-bound projects, with their tasks, whose repository is not in that user's list. A `HUMAN_MEMBER` or `REVIEWER` never reaches the delete: the response is 200 with `pruned: 0`, `pruneSkipped: "not_admin"` (`null` for an admin) and a message clause saying stale projects are only removed by a team admin; for an empty repository list that member gets both `skippedPrune: true` and `pruneSkipped`. There is no instance-wide admin, so the team role is the whole check. The prune deletes each stale project through the same service as `DELETE /api/projects/:id` (`backend/src/services/project-deletion.ts`), one grounding transaction per project: a project whose tasks carry grounding history (cohort, binding or operation rows) or a pending grounding operation is kept, not deleted, and the request stays 200. The response lists those projects in `pruneRetained` (`[{ projectId, reason }]`, `reason` is `grounding_history_retained` or `grounding_finalization_pending`, the codes the DELETE route answers with) and the message says how many were kept; `pruneRetained` is `[]` when none was. Inside each transaction the row is checked again (still this team's, repository still not in the caller's list, ignoring letter case), so a project rebound or moved after the candidates were picked is left alone; the stored attachment files of every deleted project are removed after its commit. When an admin's prune removes or keeps at least one project, one `project.synced` audit event records the team id, the actor, the candidate project ids picked (`payload.candidateProjectIds`), the ids actually removed (`payload.deletedProjectIds`), their count (`payload.deletedCount`) and the kept projects (`payload.skippedProjects`, same shape as `pruneRetained`); `payload.via` is `team_sync_prune`; no event is written when nothing was removed or kept. Repository names are compared ignoring letter case, on the lookup of the already-bound project (the exact spelling first) and on the prune, because GitHub repository names are case-insensitive, with `_` and `%` matching only themselves; an updated binding is stored back in the case GitHub reports. A repository whose write an active repository operation refuses is skipped and counted in `fenced`. When a delete is refused the same way (a stale binding is under an active repository operation), that project is left in place, the response is still 200 with `pruneDeferred: true`, the other stale projects are still pruned, and the next sync retries the deferred one. The Projects page shows both cases as a warning ("Sync partly completed") instead of "Already up to date". Run it, as a team admin, from an account that can see every repository the team tracks.
