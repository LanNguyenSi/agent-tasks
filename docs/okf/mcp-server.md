Published as `@agent-tasks/mcp-server` (npm, public). Entry point `mcp-server/src/index.ts` reads `AGENT_TASKS_TOKEN` (required, throws if absent), `AGENT_TASKS_BASE_URL` (optional, default `https://agent-tasks.opentriologue.ai`, `DEFAULT_BASE_URL` in `server.ts`), and `AGENT_TASKS_MCP_LEGACY` (optional, `"1"` to register the pruned v1 verb set, see below), then calls `runStdioServer`.

`mcp-server/src/server.ts` builds an `McpServer` (`@modelcontextprotocol/sdk`) named `SERVER_NAME = "agent-tasks-mcp"` at `SERVER_VERSION = "0.16.0"` (`mcp-server/src/server.ts:8-9`), wires it to a `StdioServerTransport`, and registers every tool from `buildTools(client, options?)` (`tools.ts`); `createServer`/`runStdioServer` both take the same optional `{ legacy?: boolean }` and pass it straight through. `mcp-server/src/client.ts` (`AgentTasksClient`) is a thin fetch wrapper: every request sends `Authorization: Bearer <token>` and `Accept: application/json`; non-2xx responses throw `AgentTasksApiError(status, body, message)`. `task_finish`/`task_merge`/`task_abandon` (`operationKey`) and `pull_requests_create`/`pull_requests_merge` (`idempotencyKey`) forward their key as the `Idempotency-Key` header (the two GitHub verbs also mirror it into the request body); when the caller omits it, `tools.ts` generates a fresh key via `crypto.randomUUID()` (`resolveOperationKey`) so provisioned completion is never sent keyless. A generated key is per call only, so a caller who needs an idempotent retry generates its own key and passes it on both the original call and the retry. That reuse holds for the two GitHub PR verbs on every backend (the legacy `/api/github/pull-requests*` routes dedupe on the body key via `backend/src/services/idempotency.ts`: one stored row per successful call, a same-key retry replays the stored 2xx with `_idempotent_replay: true`, the same key with a different payload returns 409; the Grounding GitHub router keys its durable operation on the same value). For `task_finish`/`task_merge`/`task_abandon` it holds only where the backend enforces operation keys (a provisioned task on a Grounding-configured backend); on an unconfigured backend, or for an unprovisioned task, the request either reaches the legacy handler, which ignores the key, or, for a remote merge (`task_merge`, or `task_finish` with `autoMerge`) where grounding enforcement applies to the task, is refused by `backend/src/routes/grounding-task-completion.ts` with `409 grounding_enrollment_required` before any effect. Key formats: `operationKey` and `pull_requests_merge`'s `idempotencyKey` are `/^[A-Za-z0-9._:-]{1,128}$/`; `pull_requests_create`'s `idempotencyKey` is printable ASCII without whitespace, 1-255 chars (`createIdempotencyKey`). `pull_requests_create` maps its backend `github_error` specially rather than through the generic teaching-error degrade, preserving the upstream status/body and any reconciled `existingPullRequest { number, url }` identity in the MCP error object.

**External grounding transport**: `task_grounding_attempt_create` requests a server-authorized challenge and `task_grounding_receipt_upload` forwards the producer's original signed receipt with its nominated session. Receipt text is limited to 32,768 UTF-8 bytes; the client neither verifies it nor derives completion. An external start hint projects to these MCP verbs without exposing a backend wrapper session.

**Tool surface** (`tools.ts`, one `name:` per registered tool) includes the two external-grounding transport verbs alongside the normal task verbs. `task_grounding_attempt_create` only issues an authoritative challenge; `task_grounding_receipt_upload` forwards an opaque, bounded receipt for server-side verification. It does not create a positive assessment result locally. Legacy-set verbs remain opt-in through `AGENT_TASKS_MCP_LEGACY=1`.

**Read-verb projection layer** (`read.ts`, task 3653962f): `tasks_get` and `project_tasks` are the two default-registered tools whose responses are projected mcp-server-side before going out, both through the shared `projectTaskCore` helper. `tasks_get` returns a single-task summary (`projectTaskSummary`). `project_tasks` returns summary ROWS by default: an allowlist of id, title, status, priority, labels, externalRef, createdAt, claims (work claim only, `taskListInclude` in `backend/src/routes/tasks.ts` omits the review-claim relations on this route), blockedBy, prUrl, never the full backend row, so a page of tasks with long descriptions/templateData stays small without lowering `limit` (mcp-server/src/tools.ts:803#"or include:[\"task\"] for the full, pre-contract rows.\","). Its own `include` vocabulary is narrower than `tasks_get`'s: `"description"`, `"templateData"`, `"task"`, no `"comments"`/`"artifacts"` (mcp-server/src/read.ts:268#"as const;"). Both `projectTaskSummary` and `projectTaskListSummary` guard against a malformed body (missing task(s)) at the envelope level, and `projectTaskListSummary` additionally guards each row individually: a row with no `id` (or a null row) passes through unchanged rather than crashing or silently collapsing to `{}` (mcp-server/src/read.ts:318-350#"return { tasks, nextCursor, count: tasks.length, truncated };"). `projectTaskListSummary` also carries `count` (rows in this page) and `truncated` (task e36696d7): `truncated` is `nextCursor !== null`, exact because the backend now computes `nextCursor` via a take-limit-plus-one probe (`backend/src/routes/tasks.ts`) rather than the previous `tasks.length === limit` heuristic (mcp-server/src/read.ts:328#"const truncated = nextCursor !== null;"). `signals_poll`'s own cap+cursor logic lives in the same file but is unrelated to this projection.

**Teaching errors and backlog workflow hints**: `errors.ts` maps backend error codes to MCP-layer teaching errors that include a `recipe` string and allowed-next actions. Two backlog-specific codes are taught:
  - `backlog_routing_enforced`: returned by `task_create` when an agent tries to explicitly request a non-backlog initial status. `recipe`: "omit status (or pass status: \"backlog\") on task_create; agent-created tasks always land in backlog and wait for an operator to promote them to open" (`mcp-server/src/errors.ts:787`).
  - `backlog_not_promoted`: returned by `task_start` or legacy `claim` when the task is still in backlog status. `recipe`: "this task awaits operator promotion from backlog to open; call task_respec to refine it while it waits, or task_creator_abandon to withdraw it if you created it" (`mcp-server/src/errors.ts:803`), with `allowedNext: ["task_respec", "task_creator_abandon"]` (`mcp-server/src/errors.ts:804`, the two verbs an agent can still call while it waits: refine via `task_respec`, or withdraw via `task_creator_abandon`).

The `workflow_primer` tool (`primer.ts`, a local-only tool that returns a fixed string with no backend call) documents the full backlog workflow under a "Backlog routing (v1)" section: how agent creates are routed, why backlog tasks don't appear in `task_pickup`, and the human promote/discard surface in the dashboard UI.

**Version constant guard**: `SERVER_VERSION` in `server.ts` (`"0.16.0"`, `mcp-server/src/server.ts:9`) is a separate literal from `mcp-server/package.json#version` (also `"0.16.0"`, `mcp-server/package.json:3`). `mcp-server/tests/server-version.test.ts` asserts the two stay equal, the same drift-guard pattern `mcp-bridge.md`'s own version constant test uses. Bumping the package version for a release still requires manually bumping `SERVER_VERSION` in the same change (the guard is a test, not an auto-sync), but a forgotten bump now fails the suite loudly instead of shipping a stale handshake version silently. rc-v1-C002 through C007 all landed without a version/CHANGELOG bump (deliberate); rc-v1-C008 bumped both constants to 0.13.0 and wrote the whole series' CHANGELOG in one release cut. 0.14.0 was cut later by commit `a1a4b9a` (PR #478, "chore(release): mcp-server 0.14.0, mcp-bridge 0.8.1, service 0.29.0 changelog cut", 2026-08-20), `mcp-server/CHANGELOG.md`'s `## 0.14.0` entry. 0.15.0 is `mcp-server/CHANGELOG.md`'s `## 0.15.0` entry (task f82bdbcc). The current 0.16.0 is its `## 0.16.0` entry, a pre-1.0 minor because it carries the BREAKING operation-key change.
