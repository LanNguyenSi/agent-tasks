Next.js 15 app router (`frontend/package.json`: `next@^15`). Route segments under `frontend/src/app/`: `tasks`, `dashboard` (a client redirect to the board), `projects` (the `/projects` list page plus the project hub, whose `[id]/board` tab is the board), `teams` (only `tokens`, a redirect to `/settings/team`; the legacy `/teams` list URL is a query-preserving `redirects()` rule in `next.config.mjs` pointing at `/projects`), `settings` (personal settings, with `team` for team settings), `onboarding`, `invite`, `auth`, `home`, `dev`. `frontend/src/app/api/` holds exactly two route handlers (`auth/github/route.ts`, `auth/github/connect/route.ts`) for the GitHub OAuth redirect dance, everything else talks to the backend over HTTP, there is no BFF layer.

**Board view** (`frontend/src/components/dashboard/BoardView.tsx`): a Kanban board with columns for `Backlog` (agent-created tasks awaiting human review, left of Open with a count badge), `Open`, `In Progress`, `Review`, and `Done`. The backlog column includes row-level actions to promote a task to `Open` or discard it (transition to `abandoned`); the same promote/discard actions are available in the task detail header and in the `/tasks` table. Promoting backlog to open or discarding it to abandoned uses `PATCH /tasks/:id { status: "open" | "abandoned" }` and is human-only, matching the backend contract documented in `task-lifecycle.md`. The reverse move, `PATCH /tasks/:id { status: "backlog" }` on an unclaimed `open` task, is offered as "Move to backlog" in the task detail header and in the `/tasks` table, not on the board. **Column-gated create affordance**: the header `+` button only renders on the `Backlog` and `Open` columns (`status === "backlog" || status === "open"`, `BoardView.tsx:293`): `In Progress`, `Review`, and `Done` never get one, since those are not states the pipeline can legally start a task in; they render an `aria-hidden` empty slot of the same 24px size so all five column heads are equally tall. A project with no tasks at all shows one `BoardEmptyState` (New task, Import, and Connect an agent to the project's team API tokens, shown unless the viewer is known not to be a team admin) instead of the five columns, in the board and the list view. The board page wraps its content in one focusable `#board-region` in every state, the target of the "Skip to board" link the project hub layout renders first on the board tab.

**Create modal, backlog-first default** (`frontend/src/components/dashboard/NewTaskModal.tsx`): the Status dropdown offers exactly two values, `backlog` and `open` (Backlog listed first), defaulting to `DEFAULT_CREATE_STATUS` (`frontend/src/lib/status.ts`, `"backlog"`) unless a caller (e.g. a board column's `+`) passes an `initialStatus` hint; any other incoming value is clamped back to the default. Backlog is now the default create target for human-initiated creates too, not agent-only. While the selected status is `backlog`, the Assignee `"me"` option is disabled via the `Select` component's `aria-disabled` pattern (`components/ui/Select.tsx`, not the native `disabled` attribute, so the option stays screen-reader-visible-but-unavailable rather than hidden) — self-claiming on create makes no sense for a task that is not yet promoted out of backlog.

**Page frame** (`frontend/src/components/ui/PageShell.tsx`): `/tasks`, `/tasks/[id]`, `/settings`, `/settings/team`, `/settings/team/sso` and the project hub layout (`frontend/src/app/projects/[id]/layout.tsx`) render their one `<main>` through `PageShell`, whose `variant` sets the content slot's max width (`default` 1200px, `narrow` 760px, `wide` unbounded; left-aligned unless `centered`) and whose `header` slot renders full-width bands straight into `<main>` (a sticky `PageHeader` keeps `<main>` as its containing block). The side gutter is the single `--page-gutter` token in `frontend/src/app/globals.css` (24px, 12px under 600px), used by the app header, `PageHeader`, the project hub band, the content slot and the board and tasks list bodies, so the logo, crumb, H1, first tab and first content column share one left edge. On the project hub the band (identity header and tab row) is the header slot on every tab and the board tab is `wide` and `flush` (its toolbar and board own their gutter); `/home` and `/projects` still use the older centred `.page-shell` class.

**Two list views, shared CSS not shared JSX**: `frontend/src/app/tasks/page.tsx` and `frontend/src/app/projects/[id]/board/page.tsx` are two independently-written React components (`tasks/page.tsx`'s column render helpers now live in a sibling `_components/columns.tsx`, split out because Next's typed-routes codegen rejects extra named exports from a `page.tsx`) that both render a task list. Each imports its own tree of `components/ui/*` primitives (`Button`, `Skeleton`, `StatusChip`, `Pagination`, etc.) and neither imports the other's list markup, there is no shared `<TaskList>` component. What *is* shared is the class-name vocabulary defined once in `frontend/src/app/globals.css` (e.g. both use `db-search`/`db-search-input`/`num`; `tasks/page.tsx` additionally uses a `tasks-*` prefix, `board/page.tsx` a `db-*` prefix). The tasks list includes a backlog filter, promote/discard row actions on backlog rows and a "Move to backlog" row action on open rows (disabled with a reason while the task holds a claim). Practical consequence: a visual/behavioral fix to one list (sorting, empty state, filter chips) must be manually re-applied to the other; there is no single code path to patch.

**Confidence scorer client mirror** (`frontend/src/lib/confidence.ts`, 1290 lines): a hand-maintained port of the backend scorer, used for create-time UX so `NewTaskModal.tsx` (`frontend/src/components/dashboard/NewTaskModal.tsx`) can show a live confidence score/badge before the task is even submitted (`calculateConfidence`, `ConfidenceBadge`). It is explicitly commented `FAITHFUL MIRROR ... keep in sync` with `backend/src/lib/confidence.ts`, and is now also parity-checked live in CI, see `confidence-scorer.md` for the mechanism and the exact duplicated section. `BoardView.tsx` and `frontend/src/components/TaskDetail.tsx` also import from this module directly; `TaskMetaSidebar.tsx` (`components/task-detail/`) does not import it itself, it only renders a `confidenceScore` number `TaskDetail.tsx` computes and passes down as a prop.

**Release control and effective-workflow fetch** (`frontend/src/components/task-detail/TaskMetaSidebar.tsx`, `frontend/src/lib/api.ts`, `frontend/src/app/tasks/[id]/page.tsx`, `frontend/src/app/projects/[id]/board/page.tsx`): the self-service `Release` button shows only on the viewer's own claim and never on a `done` task. In a review state it is rendered disabled with a title explaining why, instead of failing on click, because the release route answers `409 bad_state` there. The sidebar reads the server-computed `inReviewState` flag on the `Task` payload (single-task responses only), and falls back to `task.status === "review"` when the flag is absent, as on list rows; there is no frontend copy of the review-state predicate. The `getEffectiveWorkflow` fetch (`GET /api/projects/:id/effective-workflow`) runs only when `isProjectAdminRole(accessRole)` holds, in `tasks/[id]/page.tsx` and in the `board/page.tsx` task modal, and only feeds the admin status-override control; a failure there falls back to the base states and does not break the page.

**Admin claim reassign picker** (`frontend/src/components/task-detail/ClaimReassignPicker.tsx`, rendered by `frontend/src/components/task-detail/TaskMetaSidebar.tsx`, API client `getEligibleActors` and `adminReassignClaim` in `frontend/src/lib/api.ts`): a human project admin gets a `Reassign` control on the work claim (next to `Release (admin)`) and on the review claim (next to its `Release`); the button's accessible name is `Reassign work claim` or `Reassign review claim`, so the two are told apart, and `TaskMetaSidebar` takes `onClaimReassigned` as a required prop. Opening it loads `GET /projects/:id/eligible-actors`, offers every eligible human and agent except the current holder, and `Assign` calls `POST /tasks/:id/admin-reassign` for that claim; the updated task goes back through `TaskDetail`'s `onUpdate`. A 403, 409 or 400 from either call is shown inline with the server's message and leaves the picker open. Unlike the disabled-with-reason release controls it is hidden, not disabled, when `isProjectAdmin` is false, when there is no signed-in `user`, and on a `done` task. Styles are the `.td-reassign*` rules in `frontend/src/app/globals.css`.
