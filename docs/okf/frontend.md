Next.js 15 app router (`frontend/package.json`: `next@^15`). Route segments under `frontend/src/app/`: `tasks`, `dashboard` (a client redirect to the board), `projects` (the `/projects` list page plus the project hub, whose `[id]/board` tab is the board), `teams` (only `tokens`, a redirect to `/settings/team`; the legacy `/teams` list URL is a query-preserving `redirects()` rule in `next.config.mjs` pointing at `/projects`), `settings` (personal settings, with `team` for team settings), `onboarding`, `invite`, `auth`, `home`, `dev`. `frontend/src/app/api/` holds exactly two route handlers (`auth/github/route.ts`, `auth/github/connect/route.ts`) for the GitHub OAuth redirect dance, everything else talks to the backend over HTTP, there is no BFF layer.

**Board view** (`frontend/src/components/dashboard/BoardView.tsx`): a Kanban board whose columns come from `buildBoardColumns` (`frontend/src/lib/boardColumns.ts`): the `Backlog` queue (agent-created tasks awaiting human review, always the first column with a count badge) followed by the states of the project's stored workflows (`GET /projects/:id/workflows`, read by the board page for every member; a 403 or network failure reads as the built-in workflow), the default workflow's states in graph order with terminal states last, then states only present in task-pinned workflows; a task whose status matches no column lands in an extra last column, titled with the board's own name when the status is one of the five built-in state names the workflow left out and with the raw status otherwise, so every task but an abandoned one is visible (an `abandoned` task, the backend's reserved discard status, gets no column and is counted nowhere: the board has never shown it). A project on the built-in workflow shows exactly `Backlog`, `Open`, `In Progress`, `Review`, and `Done`. Promoting a backlog task to `Open` or discarding it (transition to `abandoned`) is offered in the task detail header (also inside the board's task modal) and in the `/tasks` table's row-actions menu; board cards carry no action buttons. Promoting backlog to open or discarding it to abandoned uses `PATCH /tasks/:id { status: "open" | "abandoned" }` and is human-only, matching the backend contract documented in `task-lifecycle.md`. The reverse move, `PATCH /tasks/:id { status: "backlog" }` on an unclaimed `open` task, is offered as "Move to backlog" in the task detail header and in the `/tasks` table, not on the board. **Column-gated create affordance**: the header `+` button only renders on the `Backlog` and `Open` columns (`status === "backlog" || status === "open"`, `BoardView.tsx:344`): `In Progress`, `Review`, and `Done` never get one, since those are not states the pipeline can legally start a task in; they render an `aria-hidden` empty slot of the same 24px size so all column heads are equally tall (no custom workflow state can be a start: `initialState` is locked to `open` by the backend, a tripwire test walks the shared workflow fixtures). A project with no tasks at all shows one `BoardEmptyState` (New task, Import, and Connect an agent to the project's team API tokens, shown unless the viewer is known not to be a team admin) instead of the columns, in the board and the list view. The board grid takes its column count from the inline `--db-cols` custom property (`globals.css` `.db-board`), a board with more than the five built-in columns adds `.db-board--scroll` and keeps one horizontally scrolled row with a 240px minimum column at 1280px and above (the same treatment the 761-1279px band gives every board), the list-view status chip row follows the same column list, and custom columns carry a `db-col--custom` neutral fallback class (an `--status-open` dot) with a `neutral` badge tone. The board page wraps its content in one focusable `#board-region` in every state, the target of the "Skip to board" link the project hub layout renders first on the board tab.

**Create modal, backlog-first default** (`frontend/src/components/dashboard/NewTaskModal.tsx`): the Status dropdown offers exactly two values, `backlog` and `open` (Backlog listed first), defaulting to `DEFAULT_CREATE_STATUS` (`frontend/src/lib/status.ts`, `"backlog"`) unless a caller (e.g. a board column's `+`) passes an `initialStatus` hint; any other incoming value is clamped back to the default. Backlog is now the default create target for human-initiated creates too, not agent-only. While the selected status is `backlog`, the Assignee `"me"` option is disabled via the `Select` component's `aria-disabled` pattern (`components/ui/Select.tsx`, not the native `disabled` attribute, so the option stays screen-reader-visible-but-unavailable rather than hidden) — self-claiming on create makes no sense for a task that is not yet promoted out of backlog.

**Team rename** (`frontend/src/components/settings/TeamNameSection.tsx`, rendered first on `/settings/team` by `frontend/src/app/settings/team/page.tsx`, client call `renameTeam` in `frontend/src/lib/api.ts`): the card shows an input and a Save button only when the current team's `role` is `ADMIN`; every other role sees the name as text with a note that only admins can rename. Save is disabled for a name that is blank under `isBlankTeamName` (`frontend/src/lib/teamName.ts`: only whitespace, format characters, combining marks, Hangul fillers, U+2800 or U+FFFC) or (after trimming) unchanged, and the handler refuses those too; the input sets no `maxLength` (the server counts code points and answers an over-long name with a 400 message); the trimmed name goes to `PATCH /api/teams/:id`. A saved name reloads the shell's one team list through `refreshTeams` from `useTeamList` (`frontend/src/lib/teamList.tsx`), so the header, the switcher and the API Tokens section read the new name without a page reload; the reload also runs when the card is already gone (a team switch during the request). A server error is shown in the card and the old name stays in the list. The card is keyed by team id, so a switch never carries typed text over.

**Page frame** (`frontend/src/components/ui/PageShell.tsx`): `/home`, `/projects`, `/tasks`, `/tasks/[id]`, `/settings`, `/settings/team`, `/settings/team/sso` and the project hub layout (`frontend/src/app/projects/[id]/_components/ProjectHubLayout.tsx`, rendered by the segment's `layout.tsx`) render their one `<main>` through `PageShell`, whose `variant` sets the page column (`default` 1200px, `wide` the whole width; `--page-column` on `<main>`, class `pshell--<variant>`) and caps the content slot at that column plus its gutters, centred with auto side margins, and whose `header` slot renders full-width bands straight into `<main>` (a sticky `PageHeader` keeps `<main>` as its containing block). The side gutter is the single `--page-gutter` token in `frontend/src/app/globals.css` (24px, 12px under 600px), used by the app header, the content slot and the board and tasks list bodies; the bands in the header slot (`PageHeader`, the project hub identity header and tab row, the tasks skeleton header) keep their full-width background and bottom border but pad their inner content with `max(--page-gutter, (100% - --page-column) / 2)`, so the crumb, H1, first tab and first content child share one left edge: the centred column's left edge on a default page (360px at 1920 wide) and the gutter on a wide page or a narrow screen. `/tasks/[id]` renders on the default column (flush; `.td-page` owns the gutter) and `/settings/team/sso` too, its form capped at 760px by the `sso-content` slot class. On the project hub the band (identity header and tab row) is the header slot on every tab and the board tab is `wide` and `flush` (its toolbar and board own their gutter, and the band follows that tab's column to the gutter, while members, workflow and settings align to the centred column). `/home` and `/projects` use the default column with a `PageHeader` band (the team name is the H1 on `/home`; `/projects` has the H1 "Projects" with the team and project count as its summary and Sync GitHub / New Project as band actions), and `FullPageLoader`'s `shell` variant renders the same frame (a skeleton band plus skeleton rows) so the loaded page does not jump; the older centred `.page-shell` class no longer exists. `/settings` and `/settings/team` render their own band and a busy skeleton in the same column while loading, and the `/projects/workflow` redirect states render inside a default `PageShell`, so no page switches between a viewport-centred box and the frame.

**Two list views, shared CSS not shared JSX**: `frontend/src/app/tasks/page.tsx` and `frontend/src/app/projects/[id]/board/page.tsx` are two independently-written React components (`tasks/page.tsx`'s column render helpers now live in a sibling `_components/columns.tsx`, split out because Next's typed-routes codegen rejects extra named exports from a `page.tsx`) that both render a task list. Each imports its own tree of `components/ui/*` primitives (`Button`, `Skeleton`, `StatusChip`, `Pagination`, etc.) and neither imports the other's list markup, there is no shared `<TaskList>` component. What *is* shared is the class-name vocabulary defined once in `frontend/src/app/globals.css` (e.g. both use `db-search`/`db-search-input`/`num`; `tasks/page.tsx` additionally uses a `tasks-*` prefix, `board/page.tsx` a `db-*` prefix). The tasks list includes a backlog filter, promote/discard row actions on backlog rows and a "Move to backlog" row action on open rows (disabled with a reason while the task holds a claim). Practical consequence: a visual/behavioral fix to one list (sorting, empty state, filter chips) must be manually re-applied to the other; there is no single code path to patch.

**Confidence scorer client mirror** (`frontend/src/lib/confidence.ts`, 1290 lines): a hand-maintained port of the backend scorer, used for create-time UX so `NewTaskModal.tsx` (`frontend/src/components/dashboard/NewTaskModal.tsx`) can show a live confidence score/badge before the task is even submitted (`calculateConfidence`, `ConfidenceBadge`). It is explicitly commented `FAITHFUL MIRROR ... keep in sync` with `backend/src/lib/confidence.ts`, and is now also parity-checked live in CI, see `confidence-scorer.md` for the mechanism and the exact duplicated section. `BoardView.tsx` and `frontend/src/components/TaskDetail.tsx` also import from this module directly; `TaskMetaSidebar.tsx` (`components/task-detail/`) does not import it itself, it only renders a `confidenceScore` number `TaskDetail.tsx` computes and passes down as a prop.

**Status vocabulary of the scope presets and Home widgets** (`frontend/src/app/home/widgetFilters.ts`, `frontend/src/app/home/projectWorkflows.ts`, `frontend/src/app/home/page.tsx`, `frontend/src/app/tasks/page.tsx`, `frontend/src/app/tasks/_components/useProjectWorkflows.ts`): the Home My Tasks, Priority, In Review and Done widgets and the `/tasks` Priority, My Tasks, In Review and Recently Done tabs take their status lists from the stored workflows of the team's projects (`workflowStatusNames`: non-terminal states, review-like states, terminal states; the built-in names are always listed first, so a project whose list is not loaded or not readable reads as the built-in workflow). `frontend/src/lib/workflow-vocabulary.ts` ports the backend's reading of a stored definition (`sanitizeStoredDefinition`, `isReviewState`, `terminalStates`, `safeStates`): the review-like and terminal names are judged on the sanitized definition (an entry state `backlog` reads as `open`, the backlog state and edges into backlog are dropped, an edge out of backlog is remapped only for the legacy start edge) and a definition the backend cannot read reads as the built-in `review` and `done`; `frontend/src/lib/__fixtures__/workflow-vocabulary-fixtures.ts` holds the backend's answers for both copies (`backend/tests/unit/workflow-vocabulary-parity.test.ts`, `frontend/tests/unit/WorkflowVocabulary.test.ts`). A state is review-like when it is not the initial state, not terminal, has an edge into a terminal state and is not a direct target of the initial state (`backlog` never qualifies). `terminalStatesResolver` and `reviewStatesResolver` pick the task's pinned workflow, else the project's first default row. A request asks for the union of the names across projects and the widget keeps the rows whose status has that meaning in the task's own workflow. Home asks a second time only for the widgets whose name list grew when the workflows arrived; `loadMissingProjectWorkflows` remembers a project that answered 403 (per team, cleared on a team switch) and retries any other failure on the next poll. On `/tasks` the `status` parameter keeps every state name of the URL (so the first request already carries a custom name and a 403 on a project's workflows does not drop it; the team task list does not check the names, so an unknown name lists no tasks), `statusChipsFor` adds a chip for each custom state, and the custom-filter check compares the chips with the resolved preset. Active (`ACTIVE_STATUSES`, open and in progress) is a fixed list on both pages. The `/tasks` tabs filter by name on the server, so a name with the scope's meaning in one workflow also lists that name's tasks from projects where it means something else (terminal and review-like names alike), unlike the Home widgets, which keep only the rows whose status has that meaning in the task's own workflow.

**Release control and effective-workflow fetch** (`frontend/src/components/task-detail/TaskMetaSidebar.tsx`, `frontend/src/lib/api.ts`, `frontend/src/app/tasks/[id]/page.tsx`, `frontend/src/app/projects/[id]/board/page.tsx`): the self-service `Release` button shows only on the viewer's own claim and never on a `done` task. In a review state it is rendered disabled with a title explaining why, instead of failing on click, because the release route answers `409 bad_state` there. The sidebar reads the server-computed `inReviewState` flag on the `Task` payload (single-task responses only), and falls back to `task.status === "review"` when the flag is absent, as on list rows; the sidebar has no copy of the review-state predicate (the list views have one, see the next paragraph). The `getEffectiveWorkflow` fetch (`GET /api/projects/:id/effective-workflow`) runs only when `projectCanAdmin(project)` holds (the server's `canAdmin` from `GET /api/projects/:id` when it is a boolean, `isProjectAdminRole(accessRole)` only when the response lacks it), in `tasks/[id]/page.tsx` and in the `board/page.tsx` task modal, and only feeds the admin status-override control; a failure there falls back to the base states and does not break the page.

**Admin claim reassign picker** (`frontend/src/components/task-detail/ClaimReassignPicker.tsx`, rendered by `frontend/src/components/task-detail/TaskMetaSidebar.tsx`, API client `getEligibleActors` and `adminReassignClaim` in `frontend/src/lib/api.ts`): a human project admin gets a `Reassign` control on the work claim (next to `Release (admin)`) and on the review claim (next to its `Release`); the button's accessible name is `Reassign work claim` or `Reassign review claim`, so the two are told apart, and `TaskMetaSidebar` takes `onClaimReassigned` as a required prop. Opening it loads `GET /projects/:id/eligible-actors`, offers every eligible human and agent except the current holder, and `Assign` calls `POST /tasks/:id/admin-reassign` for that claim; the updated task goes back through `TaskDetail`'s `onUpdate`. A 403, 409 or 400 from either call is shown inline with the server's message and leaves the picker open. Unlike the disabled-with-reason release controls it is hidden, not disabled, when `isProjectAdmin` is false, when there is no signed-in `user`, and on a `done` task. Styles are the `.td-reassign*` rules in `frontend/src/app/globals.css`.
