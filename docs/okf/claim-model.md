**Backlog filtering in pickup**: `POST /tasks/pickup` does not return backlog tasks at any point in its resolution order. A task in `backlog` status is invisible to both the signals branch (backlog tasks emit no `task_available` signal; see `task-lifecycle.md`) and the open-work branch. Backlog tasks are intended for human review before agent pickup; see `task-lifecycle.md` for the human promote/discard surface. A human can also demote an unclaimed `open` task back to `backlog`; it then leaves the pool the same way and its pending `task_available` signals are acknowledged, so pickup's signal branch no longer surfaces them. **D18 revision**: the CLI's id-prefix resolver (`cli/src/resolve.ts`, `cli/src/api.ts`'s `searchTaskPool`) can now resolve backlog-task IDs by prefix -- `CLAIMABLE_VALID_STATUSES` on `/api/tasks/claimable` accepts `backlog` as an explicit-search value (see the "List claimable tasks" block comment in `backend/src/routes/tasks.ts`). This is discovery only: the implicit no-params "what can I claim right now?" default still excludes backlog entirely, and a resolved backlog task's id still 403s `backlog_not_promoted` at `/tasks/:id/start`/`/tasks/:id/claim` until a human promotes it. The web UI and MCP clients could already manipulate backlog tasks directly by full UUID; only the CLI's prefix-search discoverability was the gap.

**`POST /tasks/pickup`** (agent-only; humans get `400 bad_request`, told to use `/tasks/claimable` instead) resolves "what should I do next?" in this fixed order, first hit wins:

1. **Signals**, the oldest unacknowledged `Signal` addressed to this agent (`recipientAgentId`), excluding stale ones: `review_needed`/`task_available`/`task_assigned` are dropped once their task reaches `done` (they ask the recipient to *do* something that no longer applies), but `task_approved`/`changes_requested`/`task_force_transitioned` are outcome notifications that survive even against a terminal task. The matched signal is acknowledged (`acknowledgedAt` set) atomically as part of returning it, at-most-once delivery.
2. **Review pickup**, oldest-by-`(priority desc, createdAt asc)` task with `status: "review"`, no existing review claim (`reviewClaimedByAgentId`/`reviewClaimedByUserId` both null), and `createdByAgentId !== actor.tokenId` (distinct-reviewer at the pool level, independent of `governanceMode`, see `governance-merge.md`), team-scoped, with `blockedBy: { none: { status: { notIn: ["done", "abandoned"] } } }`.
3. **Open work**, same ordering/blocking rule, `status: "open"`, unclaimed. On the first hit, `deriveDebugFlavor` runs (see below) and, if fresh or `?reclassify=true`, persists `metadata.debugFlavor` before responding.
4. **Idle**, `{ kind: "idle" }` if nothing above matched.

**Hard-limit, single active claim per agent**: both `POST /tasks/pickup` and `POST /tasks/:id/start` reject with `409 { error: "already_claimed", activeClaim: {taskId, title, role} }` if the calling agent already holds *any* active claim, an author claim (`claimedByAgentId`, `status !== "done"`) or a review claim (`reviewClaimedByAgentId`, `status === "review"`). This gate is checked first, before any other claim constraints. The two call sites duplicate this check independently (same query shape); there is no shared helper. A third copy guards the agent target of `POST /tasks/:id/admin-reassign` (below), which excludes the task being reassigned from the lookup as `/start` does. Parallelism is achieved by using multiple agent identities, not by one identity holding concurrent claims.

**Backlog guard on task_start and legacy claim**: `POST /tasks/:id/start` and the deprecated `POST /tasks/:id/claim` both return `403 { error: "backlog_not_promoted" }` if `task.status === "backlog"`, regardless of the actor's claim state. This gate is checked after the single-active-claim limit, and before the initial/review-state branches. A backlog task must be explicitly promoted to `open` by a human via `PATCH /tasks/:id { status: "open" }` before any agent can start or claim it. `mcp-server`'s teaching-error layer (`mcp-server/src/errors.ts`'s `alreadyClaimedError`/`extractActiveClaim`) passes this same `activeClaim` through, clamped, as `detail.activeClaim` on the MCP-facing `already_claimed` error, and lists `tasks_get` in `allowedNext` so a caller can check `activeClaim.taskId`'s actual status. The `backlog_not_promoted` error also includes a teaching hint, "awaits operator promotion", to guide the caller toward the human interface.

**Ordering**: every claim-pool query orders `[{ priority: "desc" }, { createdAt: "asc" }]`, highest `TaskPriority` (`LOW`/`MEDIUM`/`HIGH`/`CRITICAL`) first, oldest-within-priority first.

**Dependency gate**: `blockedBy: { none: { status: { notIn: RESOLVED_BLOCKER_STATUSES } } }` (`RESOLVED_BLOCKER_STATUSES = ["done", "abandoned"]`) at the Prisma level for pool selection, and `POST /tasks/:id/start` and `POST /tasks/:id/claim` separately re-check `blockedBy` (`unresolved = blockers.filter(dep => !RESOLVED_BLOCKER_STATUSES.includes(dep.status))`) and return `409 { error: "blocked", blockedBy: [...] }` if any blocker is unresolved, belt-and-suspenders against a race between pool selection and claim. `abandoned` counts as resolved-for-gating since task 5200f326 (treat-abandoned-as-resolved): a dependent whose sole blocker was creator-abandoned (`POST /tasks/:id/creator-abandon`, task 7a1360da) is claimable again instead of deadlocking forever; the `blockedBy` edge itself is left intact, this is a predicate change only, not auto-detach. Backlog blockers (`status === "backlog"`) count as unresolved: a task depending on a backlog task cannot be claimed until the blocker is promoted out of backlog by a human, even if no other work is actually in progress. The gate is claim-time-only and is never re-evaluated afterward: nothing hooks a blocker's status change to re-scan its dependents, so unabandoning a blocker (the admin-only `PATCH /tasks/:id` recovery path) does not retroactively re-block a dependent that already claimed while the blocker sat `abandoned`. One consequence of that design choice: an agent that created both the blocker and the dependent can resolve its own ordering unilaterally, by creator-abandoning the blocker it no longer needs to gate on (workflow ordering the creator already controlled, not an authorization boundary being crossed).

**`status` is a free `String` column**, not a DB enum: `backend/prisma/schema.prisma` declares `status String @default("open")` on `Task`. The canonical vocabulary is `backlog` (agent-created, awaiting human review), `open`, `in_progress`, `review`, `done`, and `abandoned` (terminal, unrecoverable except by admin reset). The core-workflow five-value set (`open`, `in_progress`, `review`, `done`, plus `abandoned` in the claimable-filter list) is enforced at input-schema edges: `createTaskSchema`'s Zod `z.enum([...])` on create, and `PROJECT_TASK_STATUSES`/`CLAIMABLE_VALID_STATUSES` array checks on the list/claimable query params; `backlog` is added separately on the agent-create path. Since the D18 revision above, `CLAIMABLE_VALID_STATUSES` also accepts `backlog` (search-only, no claim-eligibility change) so it now matches `PROJECT_TASK_STATUSES`'s full six-value vocabulary. The database column itself can hold arbitrary strings. The current workflow API restricts configured states to `open`, `in_progress`, `review` and `done`, requires initial `open` and only terminal `done` (`backend/src/routes/workflows.ts`, `FIXED_STATE_NAMES` and `workflowDefinitionSchema`); custom state names are not supported through that API. Legacy stored definitions are sanitized by the effective-workflow and validate-transition advisory readers as well as by task runtime resolution: backlog edges are removed, and the safe legacy start edge is remapped from open. The stored row and workflow editor view remain unchanged.

**Paging of `GET /tasks/claimable`**: the 25-row cap callers hit through MCP `tasks_list` is this route's own default page size (`limit` is 25 when omitted or non-numeric, clamps to 200 above 200 and to 1 below 1; the project task route `GET /projects/:id/tasks` differs on purpose: it caps at 500 and answers 400 for 0 or below), not an MCP-layer limit. The route fetches `limit + 1` rows, trims the look-ahead row, and always answers `{ tasks, nextCursor, truncated }`: `truncated` is true exactly when rows remain after the page and `nextCursor` is then the last returned id, `null` on the last page (an exactly-full last page is `null`, not a cursor). The id-prefix resolver in `cli/src/api.ts` follows `nextCursor` until `null`, so it is unaffected. The backend-hosted `tasks_list` tool (`backend/src/routes/mcp.ts`) takes the same `cursor` and `sort` (`createdAt:asc|desc`) inputs as the standalone MCP server and forwards them to this route unchanged, so its callers page with `nextCursor` too (both `tasks_list` tools cap `cursor` at 200 characters in their input schema; a cursor naming no task yields an empty page with `truncated: false`, since `Task.id` is a plain string); unlike the standalone tool it sets no `sort` of its own, so an omitted `sort` keeps the route default (oldest first).

**Admin claim reassignment** (`POST /tasks/:id/admin-reassign`, `backend/src/routes/tasks.ts`, directly after `admin-release`, which it leaves unchanged): a human project admin hands the work or review claim from its current holder to a chosen human or agent without releasing it first and without touching `task.status`. An agent caller is refused with `403` before any read, a non-admin human with `403`, and `hasProjectRole(..., "ADMIN")` is checked again inside the grounding transaction (`mutateGroundingRouteContext`, reason `admin_reassign`). The body is `{ claim: "work" | "review", target: { type: "human" | "agent", id }, reason? }`. The target must be in `listEligibleActors` (`backend/src/services/eligible-actors.ts`, also served as `GET /projects/:id/eligible-actors` to project admins): team members and non-`PROJECT_VIEWER` project members, deduped by user id (a user in both is reported as `team`), plus the team's non-revoked, non-expired agent tokens; a target outside the set answers `400`, and the set is read again under the lock. A claim with no holder, or a target that already holds it, answers `409` (there is no idempotent no-op, unlike `admin-release`). The single-active-claim rule applies to an agent target only, humans stay exempt: an agent that holds another active claim answers `409 already_claimed` with the same `activeClaim` shape as `/pickup`, checked inside the transaction. `checkDistinctReviewerGate` is run with the target standing in as the actor, so a project that requires a distinct reviewer cannot hand the review claim to the work claimant, nor the work claim to the current review holder (`409` both ways, checked before the transaction and again under the lock). The write is `updateMany` pinned to the holder observed at load through `withNoLiveMergeReservation`, sets the new holder's column, clears the other actor-type column and refreshes `claimedAt` or `reviewClaimedAt`; a lost write answers `409 conflict`, or `409 merge_in_progress` while a merge reservation is live. One `task.claim_reassigned` audit event is written per successful call (payload `claim`, `priorHolder`, `newHolder`, `reason`), none for a refusal. The response is `{ task, reassigned: { claim, priorHolder, newHolder } }`.

**The two review-claim writers re-check the distinct-reviewer gate under the lock** (`backend/src/routes/tasks.ts`: `POST /tasks/:id/review/claim`, reason `legacy_review_claim`, and the review branch of `POST /tasks/:id/start` on a task in review, reason `task_start_review_claim`, which the MCP `task_start` verb uses; the only two routes that grant `reviewClaimedBy*`, apart from `admin-reassign` itself, which runs the gate with the target as actor): each route runs `checkDistinctReviewerGate` once on its pre-lock read, and its revalidate runs it again against the locked row (the task with its project, as the grounding adapter loads it), next to the existing checks that the status is unchanged and the review lock is still free. An `admin-reassign` of the work claim to the reviewing actor that commits between the route's first read and the lock therefore makes the review claim answer `409` (the router's `GroundingAccessError` mapping, "Task state changed before the request completed") instead of leaving that actor with both claims. The reassign checks the opposite direction under its own lock (a work claim cannot go to the current review holder), so for a reassign and a review claim racing on the same actor exactly one side answers `409` whichever commits first. `backend/tests/integration/admin-reassign.test.ts` pins both arrival orders for both routes against Postgres by parking the two requests behind a held project row lock.

**`POST /tasks/:id/claim` takes the work claim only from the initial state and never for the review holder** (`backend/src/routes/tasks.ts`, reason `legacy_claim`): the route writes `status = startTarget`, the edge out of the workflow's initial state, so it answers `409 { error: "bad_state" }` ("Task in '<status>' cannot be claimed — must be in initial state ('<initial>')") for any other status, the rule `POST /tasks/:id/start` applies to its work-claim branch. An admin release leaves a task in review in `review` with no work claim, and before the rule `/claim` accepted that row, wrote it back to `in_progress` and skipped review; a custom workflow's unclaimed task in a non-initial state with an edge into the start target (a `blocked` task with a `blocked -> in_progress` edge) is refused the same way and has to be moved back to the initial state first, through a workflow edge into it; a workflow without a path back to the initial state needs that edge added first (a forced transition does not add a missing edge). The second rule is the distinct-reviewer gate with the review holder standing in as the claimant (the same stand-in `admin-reassign` uses for a work claim handed to the review holder, one helper for both): a project that requires a distinct reviewer answers `409 { error: "bad_state" }` ("You hold this task's review claim ...") to the actor that holds the review claim, human or agent, while a solo or opted-out project allows it. Both checks run on the pre-lock read, right after the backlog guard and ahead of the dependency, confidence and transition-rule gates, so a refusal emits none of their audit events and does not come back as the lost-race conflict; the locked revalidate repeats only the identity rule, for a review claim that lands between the read and the lock (an `admin-reassign` of the review claim to the caller, which then answers the generic "Task state changed before the request completed" `409`), because its status compare already pins the locked row to the read. `backend/tests/integration/claim-review-holder.test.ts` pins both rules, the agent holder, the custom-workflow case and that race against Postgres.

**`POST /tasks/:id/release` refuses a work claim while the task is in a review state** (`backend/src/routes/tasks.ts`, reason `legacy_release`): the self-service release resets the status to the workflow's initial state and clears only the work claim, never the review lock, so releasing from review used to leave an initial-state task with a stale review lock (the state the `/claim` rule above had to guard against). The route now answers `409 { error: "bad_state" }` ("Cannot release a work claim while the task is in review. Wait for the reviewer to approve or request changes.") for a task in any review state of the effective workflow (`isReviewState`, so a custom review-like state name counts too), on the pre-lock read right after the claimant check and ahead of the grounding wrapper, and writes nothing. It refuses in any review state; unlike `/abandon`, which lets an actor holding both claims drop them, `/release` has no such exception, so a caller that also holds the review lock (self-review allowed) gets a message naming `/abandon` (`task_abandon`) as the way to drop both. A work holder in a work state (`in_progress`) still releases to the initial state, and a status that moves to review after the read is still refused by the status compare of the locked write. The way out of a stuck review claim is the project admin's `admin-release`, which is unchanged. The caller-visible effect is on the task view's `Release` button, the `tasks_release` MCP tool and the deprecated CLI `tasks release`, which now get the `409` on a task in review. `backend/tests/integration/release-review-lock.test.ts` pins it against Postgres.

**`POST /tasks/:id/start` refuses the work claim to the review holder too** (`backend/src/routes/tasks.ts`, work branch, reason `task_start_work_claim`, the route the MCP `task_start` verb uses): a task can sit in the initial state with no work claim and the review lock still set (rows left by the earlier `POST /tasks/:id/release` of a task in review, which reset the status and kept the review lock, and by `admin-reassign`; `/release` now refuses a task in review), so the review holder could start such a task, pass every check of the work branch and end with both claims. The branch now runs the same distinct-reviewer gate as `/claim`, with the review holder standing in as the claimant (the shared helper and the shared 409 text), on its pre-lock read right after the already-claimed check and ahead of the dependency, confidence and transition-rule gates, so a project that requires a distinct reviewer answers `409 { error: "bad_state" }` ("You hold this task's review claim ...") to the actor that holds the review claim, human or agent, without emitting their audit events, while a solo or opted-out project allows it; the locked revalidate repeats the rule for a review claim that lands between the read and the lock (the generic "Task state changed before the request completed" `409`). A distinct actor can still start the released task, and the review lock stays with its holder. The pre-lock project read selects `governanceMode` along with the legacy flags, like `/claim`, so the pre-lock and in-lock checks resolve the same mode. `backend/tests/integration/start-review-holder.test.ts` seeds the stale row directly and pins the refusal, the solo project, a project whose `governanceMode` is `AUTONOMOUS` with legacy flags still requiring a distinct reviewer, the agent holder and the race against Postgres.

**Forced transitions are admin-only**: `POST /tasks/:id/transition` with `{ force: true }` returns `403` unless `isProjectAdmin(actor, task.projectId)`, checked unconditionally, before the workflow-precondition evaluation, specifically so a non-admin can't bypass the distinct-reviewer gate merely by having no failing preconditions to force past.

**`debugFlavor` lazy classification**: see `task-lifecycle.md`.

**Grounding context on direct claim changes**: author/reviewer acquire and
release, admin release, admin reassign, creator-abandon, and admin recovery from `abandoned`
use the shared parent-before-task transaction protocol. Authority and the
expected claim/status are rechecked under lock; a changed compare-and-swap
supersedes the active grounding attempt, advances its context generation, and
records the context mutation with the existing claim/audit semantics. A zero-row
CAS or other no-op commits without invalidating again. An unresolved durable
finalization reservation blocks these mutations until recovery resolves it.

**Member removal is a context mutation**: removing a project member selects
that member's active work and review claims after the project lock. It clears
the live claim fields, invalidates the selected attempts, writes the mandatory
context audit, and deletes the membership in one transaction. An active
finalization reservation rejects the whole removal before either a claim or
membership changes, and so does a merge reservation: a task whose pull request
is being merged keeps its claims, the removal answers `409 merge_in_progress`
and the member stays (`backend/src/routes/invites.ts`, `backend/src/services/task-merge-reservation.ts`). Workflow and project-member writers now use this boundary; configured GitHub
creation and webhook writers participate in it too (see `governance-merge.md`
and the [receipt contract](../grounding-receipt-contract.md)). Public MCP
transport remains separate follow-up work.

Related: `workflow-gates.md`, `governance-merge.md`, `task-lifecycle.md`.

An independent administrative hold is checked before cohort selection or unprovisioned fallback. It blocks fresh task completion and evidence use, including force/override paths; the database guard freezes all task-row updates and deletes. Existing claims and cohort history remain stored. See [migration and resume](../grounding-migration.md).

Runtime-selected REST creation still puts agent-created tasks in backlog. The same explicit selection covers signed issue-open deliveries, which preserve `open` after validating it is an existing non-review, nonterminal workflow state. Enrollment and task creation commit together; webhook creation adds no claim or availability signal.
