**There is no deploy automation in this repo.** `.github/workflows/ci.yml` (triggered on push to `master`/`main`/`develop`/`release/*`, on PRs to `master`/`main`/`develop` only, plus `workflow_call`/`workflow_dispatch`; both push and pull_request triggers skip the run entirely for `**.md` and `docs/**` changes via `paths-ignore`, `ci.yml:6-11` and `ci.yml:14-19`) runs five jobs, `backend` (Postgres 16 service container, native-dep smoke test, Prisma generate, typecheck, lint, `test:coverage`), `frontend` (a vendored-fonts guard step that fails when the Google fonts loader is imported or when its grep errors, typecheck, lint, `test:coverage`, `next build`, run twice under a `matrix: node-version: [22, 26]` as "Frontend (Node 22)" / "Frontend (Node 26)", `ci.yml:93-95`), `mcp-server`, `mcp-bridge` (`needs: mcp-server`), `cli`. `.github/workflows/docker-smoke.yml` also builds the frontend prod image and boots the container on frontend-touching PRs (`tools/frontend-docker-smoke.sh`: build `--target prod`, run, assert `GET / -> 200`, fail on container exit) -- a pre-merge image-viability guard, still not a deploy. A second phase boots the frontend service via `docker-compose.prod.yml` itself and asserts the compose-declared healthcheck reaches `healthy` (single-sourced -- the script re-encodes no probe parameters); `tools/compose.smoke-override.yml` detaches that smoke container from the shared external `traefik` network and sets `traefik.enable=false` so a smoke run on a proxy-carrying host can never join the live route, and the script verifies that detachment on the live container at runtime. A second job, `backend-prod-images`, runs `tools/backend-docker-smoke.sh`: it builds the `migrate` and `backend` (`--target prod`) services of `docker-compose.prod.yml`, starts `db` and `migrate` and requires migrate to exit 0 within a bound, starts `backend` and polls `GET /api/health` inside the container for HTTP 200 with `dependencies.database.status` ok (that route runs `SELECT 1`), then requires the compose-declared backend healthcheck to reach `healthy`; a crash-looping container (restart count above zero), a failing migrate or a timeout fails the job with the service logs, and teardown always runs. The same override file detaches the smoke backend from `traefik`. The workflow's path filters include `backend/Dockerfile`, `Dockerfile.migrate`, `backend/src/**`, `backend/tsconfig.json` and `backend/prisma/**`, so those changes trigger it; it is still not a required check. Nothing in `.github/workflows/` pushes an image, SSHes anywhere, or calls a deploy webhook. `docs/deploy-verify-strategy.md` makes this an explicit design decision, not an oversight: deploy/verify are modeled as "operational follow-ups," not task-workflow states, `done` means the modeled lifecycle is complete (review approved, or the PR merged via `task_merge`/`pull_requests_merge` or a GitHub merge in `AUTONOMOUS`; the default workflow also keeps an `in_progress → done` edge that requires a branch and a PR, `backend/src/services/default-workflow.ts`), not that the change is live (ADR 0014). Deploy and verify are not modeled as workflow states by default: customizing the default or applying a registered template (`backend/src/services/workflow-templates.ts`) copies a four-state definition, and although the workflow API accepts custom state names for a workflow it creates or updates (`workflowDefinitionSchema` in `backend/src/routes/workflows.ts`, with the initial state pinned to `open` and `backlog` and `abandoned` reserved, see `claim-model.md`) the workflow editor cannot author them, so teams track deploy and verify outside task status, as comments, labels or follow-up tasks.

**Prod runtime** (`docker-compose.prod.yml`): `db` (`postgres:16-alpine`, named volume `agent_tasks_postgres`, healthcheck `pg_isready`) → `migrate` (one-shot, `Dockerfile.migrate`, `depends_on: db: condition: service_healthy`, `restart: "no"`) → `backend` (`depends_on: migrate: condition: service_completed_successfully`; with a `node -e fetch` healthcheck on `127.0.0.1:3001/api/health` -- interval 5s, timeout 5s, retries 3, start_period 20s -- so Traefik, which only routes healthy containers, de-routes a backend that is up but not answering) → `frontend` (`depends_on: backend`, so it waits for `migrate` only transitively; with its own `node -e fetch` healthcheck on port 3000 -- interval 5s, timeout 5s, retries 3, start_period 10s -- whose comment in the compose file documents the measured detection bounds and the Traefik coupling: Traefik's Docker provider, with its default `allowEmptyServices=false`, only routes containers whose health is `healthy`, so the public route appears with the first successful probe and an unhealthy frontend is de-routed to a public 404 that self-heals on the next successful probe). `backend` builds its `DATABASE_URL` from the optional `POSTGRES_APP_USER` and `POSTGRES_APP_PASSWORD` (falling back to the owner role `agent_tasks` and `POSTGRES_PASSWORD`), so it can run as a separate role that is not a superuser and owns no table (set both or neither); `migrate` always connects as the owner role (grants in `docs/grounding-migration.md`, "Runtime database role"). `backend` also forwards these optional settings from the deployment `.env`, each with an empty default that the backend treats like an unset variable: `ANTHROPIC_API_KEY`, `AGENT_TASKS_REWRITE_MODEL`, `WEBHOOK_ALLOWED_PRIVATE_HOSTS`, `ATTACHMENT_MAX_COUNT_PER_TASK`, `ATTACHMENT_MAX_TOTAL_BYTES_PER_TASK`, `ARTIFACT_MAX_COUNT_PER_TASK`, `ARTIFACT_MAX_TOTAL_BYTES_PER_TASK` and `AGENT_TASKS_DISABLE_GROUNDING`, plus `SSO_ENCRYPTION_KEY`, `BACKEND_URL`, `IDEMPOTENCY_TTL_DAYS` and `REDIS_URL`; `backend/src/config/index.ts` maps an empty `BACKEND_URL`, `REDIS_URL` or `IDEMPOTENCY_TTL_DAYS` to unset (`emptyAsUnset`) so the schema default applies, and `SSO_ENCRYPTION_KEY` defaults to the empty string; a variable outside the `environment:` block never reaches the container. `migrate`'s `Dockerfile.migrate` installs the backend workspace with `--ignore-scripts`, copies only `backend/prisma`, and its `CMD` runs `npx prisma db push --schema=/app/backend/prisma/schema.prisma --skip-generate` followed by `npx prisma db execute --schema=/app/backend/prisma/schema.prisma --file=/app/backend/prisma/grounding-github-fence.sql` and `npx prisma db execute --schema=/app/backend/prisma/schema.prisma --file=/app/backend/prisma/clear-terminal-claims.sql` under `sh -c` with `&&`. The first SQL installs the repository-fence triggers. The second is a data repair that clears the work and review claims of every task in a terminal state of its own workflow (pinned workflow, else the project default, else the built-in one); it is idempotent, so it runs on every deploy and changes nothing once the leftovers are gone, and it skips (with a notice) a task a Grounding hold or an active repository fence refuses to write, which the next run picks up. Any command failing prevents successful migration completion and backend startup. Local `npm run db:push --workspace=backend` runs the same two SQL files after schema sync. Schema sync uses `db push`, not `migrate deploy`; **`--accept-data-loss` is not passed**, so a column/type change that Prisma judges destructive makes `migrate` exit non-zero and `backend` is not started; Prisma warns for any UNIQUE constraint added, with or without duplicates, as well as for dropping a populated column or table. Such a deploy always recreates the backend (its image copies `backend/prisma`) and usually the frontend, and compose leaves the recreated services in `Created` state, so the whole site is down until agent-relay's automatic rollback completes (and stays down if that is blocked). A destructive change is applied deliberately with the backend stopped, a backup and a one-off `docker compose -f docker-compose.prod.yml run --rm --no-deps migrate sh -c "npx prisma db push ... --accept-data-loss"`, described in `docs/ops-backups.md` ("Applying a destructive schema change").

`backend` and `frontend` both join two Docker networks: `internal` (talks to `db`) and the external `traefik` network, with Traefik router labels for `agent-tasks.opentriologue.ai` (`/api`+`/docs` prefix → backend port 3001; everything else → frontend port 3000), TLS via `letsencrypt` cert resolver. `backend` has an uploads volume (`agent_tasks_uploads`) for human-uploaded attachments, explicitly called out in the compose file as **not** covered by the Postgres backup scope. The file sets an explicit project name, `name: agent-tasks` (the name compose derived from the deploy checkout's directory before, so the volumes keep theirs), and `docker-compose.yml` sets `name: agent-tasks-dev`, so a bare `docker compose` command in the same directory cannot adopt the prod stack; the prod file always needs `-f docker-compose.prod.yml`. The public domain comes from `APP_DOMAIN` (default `agent-tasks.opentriologue.ai`) in the Traefik rules, `FRONTEND_URL`, `CORS_ORIGINS` and the frontend build arg `NEXT_PUBLIC_API_URL`. Every service uses the `json-file` log driver with `max-size` 10m and `max-file` 3. `TRUSTED_PROXY_HOPS` defaults to 1 in the prod file and to 0 in the dev file and `.env.example`. Memory limits are hand-tuned per service (`db` 512m, `migrate` 512m, `backend` 768m, `frontend` 1g) based on observed idle/peak RSS, documented inline.

**Verifying a deployment**: since there is no in-repo mechanism, verification is external, confirm the `backend`/`frontend` containers are healthy and on the expected image digest, hit `GET /api/health` AND the root URL (a healthy backend says nothing about a crash-looping frontend), and check the Traefik router is serving the current cert/host. `tools/frontend-docker-smoke.sh` and `tools/backend-docker-smoke.sh` cover pre-merge image viability; there is still no scripted post-deploy verification in this repo -- that is an ops runbook outside `docs/okf/`.

## Deployment checks for grounding migrations

Grounding migration inventory is a read-only deployment check. Use `node scripts/grounding-deployment-check.mjs --inventory-only` with an explicit `GROUNDING_MIGRATION_DATABASE_URL` after building the backend. Its result is an input to a migration review, never a readiness decision or an activation command. A valid pinned legacy `complete` phase is reported as compatible rather than as a repair request; malformed or impossible legacy phase data remains a repair signal.

Review the inventory together with an isolated backup/restore rehearsal, additive-schema mixed-version exercise, and proof that old writing instances are excluded before any enforcement change. A report that recommends a hold does not enforce one. A valid hold needs an authorized migration and a maintenance mechanism that participating writers cannot bypass.

Do not activate from inventory counts, a successful process exit, a package version, or a caller flag. Keep activation blocked until the explicit runtime configuration and new-task cohort selection are reviewed, writer-fleet exclusion is demonstrated, and separate host/operator key and state evidence is complete.

Related: `architecture.md`, `release-flow.md`.

The canonical fence SQL also installs the task UPDATE/DELETE hold guard, the migration-overlay repository fence and immutable-command guard. Hold entry advances the task row version; schema sync alone is insufficient. Inventory adds held counts while remaining read-only. The [migration procedure](../grounding-migration.md) describes the optional admin path and still requires separate fleet/deployment qualification.

Compose forwards `GROUNDING_RUNTIME_CONFIG` with an empty default. The backend checks runtime configuration and database prerequisites before listening. Empty configuration requires all grounding tables to exist, and every row across them requires configured routing, including completed and inactive history and every `grounding_github_fence_intents` row, with one exception: the repository-fence SQL trigger bumps an unowned `grounding_github_repository_fences` row on any ordinary GitHub-linked task write whether or not grounding is ever configured, so an unowned fence row is not treated as history on its own; an *owned* fence still requires configured routing. Installing without ever configuring grounding needs no special handling. Enabled configuration also derives an enforced scope from `creationPolicy`, composes the effect-boundary check that every legacy GitHub write runs over that scope, and refuses startup when a project outside it shares a GitHub repository with a selected project, when a selected project's repository is not a canonical `owner/repo` identity, or, while the scope owns a repository, when any project's repository is not canonical. Enabling configuration writes grounding history (webhook deliveries, for example), so it is one-way: rollback means keeping an enabled configuration with empty trust and an empty `creationPolicy`. Preserve valid configuration for restore and compatible rollback, and coordinate restarts for trust rotation or revocation. See [configuration and upgrade](../grounding-migration.md).
